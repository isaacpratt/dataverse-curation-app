Plan: replace the dvmeta crawl with in-process dashboard enrichment

Goal: give every user — including frozen exe users, who can never run dvmeta — the rich dashboard data (exact sizes, true depositors, authoritative draft state) with zero new dependencies, then delete the dvmeta branch and its pins. Recommended: Option A No new dependencies Exe users gain, nothing lost

Decisions recorded 2026-10-07 (review session): Direction Option A; scope = drafts-first, row-cap-200, sums-only, cache-write-back, pool workers = 5. Approved: W-01 – W-05 (enrichment build + tests). Deferred: W-06 – W-08 (dvmeta removal, depin/docs, live verification — after enrichment proves out). Evidence: full Borealis ≈ 25,000 datasets; largest curated collection ≈ 1,300 datasets; entire collection must load without blocking other parts. ⚠ 1,300 exceeds the current Search cap (max_pages=10 → 1000) — discovery cap must be raised alongside W-01 (proposed: default max_pages=15, i.e. 1500, Truncated warning retained).

1 · Current state: two divergent dashboard backends

The "core" worth keeping is one operation: fetch the full draft datasetVersion doc per dataset and run it through normalize_files(). The Search API cannot return those fields (Solr docs don't carry them). We already own both halves: get_file_inventory() dataverse_client.py:2054 and pooled concurrent I/O in CrawlWorker ui/workers.py:81,197.

2 · Desired behavior

  • One discovery path for everyone: Search (≤10 pages) → pooled get_file_inventory enrichment for draft rows → dashboard paints instantly from thin rows, then patches Size / Depositor / Status cells progressively.
  • Enriched fields persist into dashboard_cache.json so reopen is instant and rich.
  • dvmeta branch, pins, and docs references deleted; no new dependency; frozen behavior unchanged in shape, richer in data.

4 · Proposed approach (4 phases)

Phase A — enrich

Post-search enrichment in CrawlWorker: pool-fetch get_file_inventory for rows missing sizes (drafts first), bounded workers, per-completion progress. Touchpoints: dataverse_client.py (new bulk helper), ui/workers.py:79–90 (existing pool pattern to mirror).

Phase B — guards

Row cap (default ~200, tail shows "pending"), 429 respect via existing backoff, cancel/adopt on view close per existing lifecycle, progressive cell patch + cache re-save. Touchpoints: ui/dashboard.py, dashboard_cache.json + diff_dashboard_datasets.

Phase C — remove

Delete _crawl, the list_draft_datasets dvmeta branch, _dvmeta_available/_dvmeta_cli_path, and the parse_ds_metadata_payload branch (keep or repoint its one test engine/tests/test_dataverse.py:66); depin requirements.txt:5 + pyproject.toml:15; update dataverse-integration.md, architecture.md, development.md, user-guide.md, README context row.

Phase D — verify

New tests: enrichment sums/counts, cap + "pending" behavior, cancellation, per-item error isolation. Live-verify against https://demo.borealisdata.ca (13 datasets / 2 pages baseline) and note wall-clock vs today.

Deliberate non-goal: do not embed full per-row files arrays in dashboard state (memory-growth smell noted at ui/dashboard.py:361). Enrich with sums + counts + depositor + state only; the detail view already refetches full inventory on open via MetadataWorker.
