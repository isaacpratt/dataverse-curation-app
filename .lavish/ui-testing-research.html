Why UI fixes keep breaking, and what to do about it

Research draft for Dataverse Docent (PySide6 desktop) — best practices, testing tools, and the rewrite question. Written, self-critiqued, and revised. Design: the app's own tokens (Inter, #004ccd on #faf8ff, 8px radius).

VerdictStay on PySide6. The regression risk is testing architecture + no screenshot gate, not the framework. Add 3 cheap harnesses first; rewrite buys almost nothing and costs the engine port. ConfidenceHigh that stay-and-harden wins (2026 comparisons concede Tauri smaller but Qt more mature; our size problem is Python libs, not Chromium). Medium on the exact rollout order — needs your call on baselines policy. ScopeNo project code changed. This is docs only.

1. What's actually breaking

Constant fix→break→new-issue cycles in this app trace to three structural gaps, not authorship sloppiness:

  • No golden images. Visuals are verified by eye and geometry probes (tools/probes/) that assert sizes, not painted pixels. A tutorial probe can prove a header is 36px and still miss a clipped glyph or wrong tint.
  • QSS hides what tests can see. Inline style sheets replace application styles subtree-wide in Qt, so a local sheet silently un-themes descendants. The repo already guards this with test_theme_conformance.py — good — but there is no pixel-level backstop when a mixin drifts.
  • One-off measurements. Several past fixes were verified with ad-hoc one-off probes and then the probe was discarded, so the next change re-breaks it. Rules that live only in a probe are not rules.

Evidence: theme/kit split (palette → role → component), contrast contract + gallery (ui/gallery.py), translated header-casing fix (sentence case lives in model data so Qt measures what it paints).

2. Best practices for Python + PySide6

PracticeWhatWhy it stops regressions
Model/View separationKeep data in QAbstractItemModels; views are standard QAbstractItemViews. Qt merges View+Controller into the widget, so separation means data vs. presentation.Same model, many views; a view change can't corrupt stored data.
Widgets for information-dense tools, QML for fluid/animated UIsOfficial and community consensus: Widgets = forms/tables/dialogs that should feel native; QML = touch/animated/custom.Picks the mature local conventions over bespoke chrome you must re-verify forever.
Component gallery as living contractui/gallery.py rendering every kit component is the PySide equivalent of Storybook.Exhibits defaults; a mixin change shows up in one place with evidence.
Tokens, not literalsNo raw hex / font-size outside theme.py (already enforced by tests).One place to change a color or size; drift fails the build.
pytest-qt for interactionqtbot fixture (mouse/keyboard), waitSignal, auto-capture of qDebug/exceptions.Proves behavior, not just appearance (click → state, hover → tooltip, Tab order).

4. Would a rewrite help?

OptionTestabilityCost vs. our app (Python engine + Qt UI, Windows-only)
Stay: PySide6 WidgetsHigh, with pytest-qt + goldens + galleryReuses the 212-test engine, theme/kit, gallery, PyInstaller lite build. Risk is bounded.
Qt Quick / QMLGood (QML Test + TestCase), but custom rendering loses native conventionsSame engine can stay, UI restyle is large; Community consensus keeps Widgets for form-heavy desktop tools. No regression benefit over Widgets.
Tauri v2 (Rust + webview)High for web layer (Playwright/webdriver), but UI logic rewrites to a new languageBest bundle-size story (3–15MB vs Electron 85–200MB), but we'd re-port the R/python engine and re-build the whole kit. 2026 comparisons call a Tauri migration "closer to a rewrite than a refactor".
ElectronHigh (Playwright/Storybook/Chromatic stack)Brightest testing ecosystem — and the wrong answer for us: 85–200MB, Chromium download, duplicates the OS webview we already solve with Qt. Solves our test problem by changing the problem.
Flutter DesktopGood (golden tests + widget tests); pixel-perfect everywhere15–25MB, Dart rewrite of engine (no Python libs), loses native theming. Interesting, not justified.

Verdict: no rewrite. Every rewrite candidate trades a known, small problem (add 2 harnesses) for a large one (re-port the engine, rebuild the kit, re-validate every check). Electron's testing advantage is real but you pay 100MB+ and a language move to get it. The mature answer is: same stack, better gates.

5. Recommended rollout (phased, reversible)

Phase 1 — Screenshot goldens (biggest ROI)

  • Checked-in baseline directory; test_golden.py grabs each page + gallery + dashboard states offscreen, diffs vs baseline with per-image tolerance (fonts/AA ⇒ threshold, not exact).
  • Baselines update only via explicit --update-baseline; drift prints the diff image.
  • What it catches: wrong tint after a token swap, clipped text, shifted headers — the exact class that today needs a human glance.

Phase 2 — Behavior contracts

  • pytest-qt tests for the repeated bugs: header casing vs elision, focus tint on keyboard-only, split-chip elision + tooltip, dirty-guard prompts, sort indicators.
  • Each past fix gets one regression test that names it (no discarded probes).

Phase 3 — Process

  • Gallery renders in CI and is diffed as goldens — the exhibit is the test.
  • New components must land in the kit + gallery + golden in one PR (the conformance tests already enforce kit use; extend them with a "gallery coverage" check).

6. Critique of this draft (and what changed)

I wrote a first draft, attacked it, and revised. The honest weaknesses:

Self-critiqueHow the final report fixed it
Draft leaned on Squish as "the answer" — pricing and licensing buried in a footnote.Squish demoted to a conditional tool with an explicit cost and a "not for us yet" verdict.
Treated Electron's test ecosystem as a pure win; ignored that bundle and team cost double.Electron reframed as "solves our test problem by changing the problem" with size numbers called out.
Recommended pixel-exact goldens, which flake on font/AA/DPI differences.Now threshold-based with per-image tolerance and a pinned offscreen environment.
Assumed the gallery is enough; it isn't — someone must look at it.Phase 3 makes the gallery itself a CI golden, so looking is automated.
First draft justified rewrite with bundle size; our size is Python libs (~174MB lite folder), not Chromium.Size corrected: rewrite doesn't shrink our problem; Tauri's 3–15MB win doesn't apply to a Python engine we keep.

Remaining blind spots, stated plainly: I did not benchmark baseline flakiness across Windows font rendering, did not spec the diff threshold, and did not pick a pixel-diff library (Pillow diff vs. opencv vs. pixelmatch-style) — that choice comes with a Phase-1 prototype, not this paper.
